## 4. Composite grade

Weighted composite (LongMemEval accuracy 40%, retrieval recall 20%, abstention 15%, token efficiency 15%, latency p95 10%): **C**

Grading rubric (documented, re-derivable):

* Accuracy: S >= 95%, A >= 90%, B >= 80%, C >= 70%, else D
* Retrieval recall (oracle evidence inside the built context): S >= 95%, A >= 90%, B >= 85%, C >= 75%, else D
* Abstention (accuracy on unanswerable/probe questions): S >= 95%, A >= 90%, B >= 80%, C >= 70%, else D
* Token efficiency (context tokens/question): S <= 500, A <= 1000, B <= 2000, C <= 4000, else D
* Latency p95: S <= 2000 ms, A <= 4000 ms, B <= 8000 ms, C <= 15000 ms, else D

Multi-hop / single-hop / contradiction / instruction-following / summarization slices are reported but unweighted (they have no published Mem0/LongMemEval counterpart to compare against).

## 6. Deterministic memory engine (answer committer)

Doctrine: *the reader is not asked to be smarter; the runtime removes the places where it can be wrong.*  Each row is one frozen measurement produced by `scripts/benchmarks/commit_sweep.py --report-out ...`; the aggregator reads raw counts only, so every ratio below is re-derived and no percentage is averaged.

| Measurement | N | Deterministic coverage | Commit accuracy | Reader on same set | Commit delta | Fallback rate | LLM calls saved |
|---|---:|---:|---:|---:|---:|---:|---:|
| LongMemEval - all types | 500 | **11.8%** (59) | **93.2%** | 89.8% | +0.40pp | 88.2% | 59 |
| LoCoMo 1,540 - category 2 (temporal) | 321 | **34.0%** (109) | **70.6%** | 67.0% | +1.25pp | 66.0% | 109 |
| **Total (all measurements)** | 821 | **20.5%** (168) | **78.6%** | 75.0% | +0.73pp | 79.5% | 168 |

KPI definitions (re-derivable from the stored counts):

* **Deterministic coverage** = questions answered by the runtime with **0 LLM calls**, `claimed / n`; the parenthesised number is the raw count.
* **Commit accuracy** = `commit_correct / claimed` - the accuracy of the committed answers. A skill has to defend this before it may bypass the reader.
* **Reader on same set** = the *paired* frozen reader run's accuracy on exactly the same questions; the counterfactual the committer has to beat.
* **Commit delta** = `(commit_correct - reader_correct) / n`, i.e. the net effect on the whole slice, not on the claimed subset.
* **Fallback rate** = `1 - claimed / n` - the share still handed to the LLM reader.
* **LLM calls saved** = `claimed` - every committed answer replaces one reader call (and its latency) with a deterministic one.

## 7. Model sensitivity (same slice, smaller reader)

Doctrine: *a score belongs to the runtime only where it survives a weaker reader.*  Each row pairs two runs that differ in exactly one thing, `--model`: same context cache, same questions, same prompt, same matcher, same committer threshold; `scripts/benchmarks/model_sensitivity.py` writes them.  Every question falls into both-correct / A-only / B-only / both-wrong, and only the counts are stored, so the accuracies, the delta and the p-value below are re-derived here.

Readers paired: A = `qwen2.5:7b-instruct` vs B = `qwen2.5:1.5b`, A = B = `qwen2.5:1.5b` (repeat control), A = B = `qwen2.5:7b-instruct` (repeat control).
Repeat controls (`LoCoMo 1,540 - category 2 (temporal) - repeat control 1.5B`, `LoCoMo 1,540 - category 2 (temporal) - repeat control 7B`) pair a reader with itself across two runs that differ only by the committer flag, so their delta is the run-to-run noise floor every other row has to clear.

### 7.1 Where the delta lives: the deterministic zone vs the LLM zone

| Zone | N | Reader A | Reader B | Delta | A-only | B-only |
|---|---:|---:|---:|---:|---:|---:|
| Deterministic zone (0 LLM calls) | 109 | 70.6% | 70.6% | +0.00pp | 0 | 0 |
| LLM zone (the reader still answers) | 1872 | 68.1% | 67.3% | +0.75pp | 172 | 158 |

The deterministic zone is an invariant rather than a result: questions answered by code score identically under both readers, so that zone contributes exactly 0 to every delta above.
Neither arm skipped the reader in `LoCoMo 1,540 - category 2 (temporal) - readers only`, `LongMemEval 500 - deployed configuration`, so that slice's deterministic row is the readers' own accuracy on the questions the deployed committer answers with no LLM call - it is held out of the zone table above, and the operational model-sensitivity number for those slices is the LLM-zone row.
The zone rows cover 1981 of 2040 pooled questions: 59 in counterfactual deterministic rows (both arms answered them as a reader), held out so the deterministic row keeps meaning 'code answered it'.

Pairing controls: the context is not re-retrieved between the two arms, so the per-question token count and oracle recall have to match exactly. 5 of 5 slices show no drift.
Question sets nest in 1 slice(s): LoCoMo 1,540 - category 2 (temporal) - readers only - arm B covers arm A plus questions outside this slice, which are excluded rather than mismatched.

KPI definitions (re-derivable from the stored counts):

* **Reader A / Reader B** = `(both_correct + a_only) / n` and `(both_correct + b_only) / n` - the two arms of one slice.
* **Delta** = `(a_only - b_only) / n` in points: the paired difference between the two readers on identical inputs. Near zero means the runtime absorbed the model difference; large means the score belongs to the reader.
* **A-only / B-only** = questions exactly one reader answered correctly - McNemar's discordant pairs.
* **p (exact)** = two-sided exact McNemar over those pairs, no chi-square approximation, because the discordant counts are small. A large delta riding on a handful of flips is not yet a finding.
* **Bigger-reader share** = `a_only / (a_only + b_only)`; 50% means the two readers disagree at random.

## 8. Failure ceiling (where the remaining score is stuck)

Every wrong answer of the deployed LoCoMo-1,540 arm (`temporal321_rules_commit_7b_postfix.oraclefix.json`, 109 answered by the committer) lands in exactly one bucket, and the buckets sum to the 544 failures. `scripts/benchmarks/failure_ceiling.py` writes them; the reader accounting comes from the §7 pairing.

| Bucket | Questions | Share of slice | Share of failures | What it is |
|---|---:|---:|---:|---|
| retrieval | 134 | 8.7% | 24.6% | the gold evidence turn is not in the compiled context |
| commit | 32 | 2.1% | 5.9% | the committer claimed it and the committed answer is wrong |
| unresolved reader sensitive | 103 | 6.7% | 18.9% | evidence present, and the other reader got it right |
| unresolved reader insensitive | 275 | 17.9% | 50.6% | evidence present, and no reader in the pair can |

**Only 264 of 1540 questions (17.1%) change outcome with the reader at all**, and 413 are wrong for both readers. That is the number that decides where effort goes: a bigger reader cannot address most of what is left, and neither can a bigger retriever - see the unresolved row.

### 8.1 Gold-context ceiling (what survives the evidence being handed over)

The 378 unresolved questions replayed through the frozen runner with **only the gold evidence turn(s)** - 66 words against the production context's 1,590:

| Outcome with the gold context | Questions | Share |
|---|---:|---:|
| recovered by **both** readers - the context was the blocker | 15 | 4.0% |
| recovered by the 7B only - a capability gap | 10 | 2.6% |
| recovered by the 1.5B only - distrust until reproduced | 56 | 14.8% |
| recovered by neither | 297 | 78.6% |

**On 272 of the 297 questions that fail for both readers (91.6%), the gold answer is not in the labelled evidence at all.** A reader cannot be wrong about a fact that is not in front of it, so that mass needs a deterministic **derivation** layer - temporal arithmetic, a join across turns - not a better retriever and not a bigger reader. Caveat: the gold context is built from LoCoMo's labelled evidence ids, so this figure mixes derivation-needed with label-under-specified.

### 8.2 Provenance of the retrieval oracle

Earlier internal runs used a **label-based** oracle (did the gold evidence *id* appear in the compiled context?). An audit showed the context compiler numbers the turns it emits in its own group order, so those ids are not the dataset's ids: the flag was wrong on **22% of the slice in both directions** while the aggregate barely moved. Every ceiling number above is recomputed with content+date evidence matching; the label-based figures are kept below rather than deleted.
