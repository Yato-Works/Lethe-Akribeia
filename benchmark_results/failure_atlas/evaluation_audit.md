## Scorer version — and why stored flags are not reused

The stored `is_correct` came from the scorer **before** `c449aa0`, which credited
a **wrong DATE** as correct whenever month and year agreed:

```
pred '10 May, 2023'  gold '27 May, 2023'   ->  was scored CORRECT
pred '25 June, 2023' gold '24 June, 2023'  ->  was scored CORRECT
```

Root cause: the 60%-token-overlap rule filters tokens with `len(w) > 2`, dropping
1–2 digit day numbers, so `may` and `2023` carried the whole score.

**Every prediction in the atlas is therefore RE-SCORED** with
`eval_locomo_full.score` at revision `c449aa0`. The stored flag is kept alongside
as `stored_is_correct` for comparison, and the difference is recorded as
`scorer_changed_verdict`.

## Join integrity

Question texts carry **different id formats** between the two files
(`lc_conv-26_0` in predictions vs `conv-26-qa-000` in the cache), so the join is on
**normalised question text**, not on id.

| check | result |
|---|---|
| predictions loaded | 1,986 |
| unique question texts | 1,974 |
| duplicate question texts | 12 (11 identical, 1 conflicting) |
| joined predictions ↔ cache | 1,974 / 1,974 — no orphans either side |
| category agreement across the join | 1,974 / 1,974 |
| gold mismatches vs dataset | 0 |

**The 12 duplicates.** 11 are byte-identical in gold and prediction and are
collapsed to one atlas record each. 1 conflicts and is reported rather than
silently resolved:

```
qid  lc_conv-48_72  pred '2003'  gold '2003 when she was 10'
qid  lc_conv-48_98  pred '2013'  gold '2003 when she was 10'
```

Both are excluded from the atlas (first occurrence wins), so the conflicting
pair is **not** counted in any cluster. This is a dataset defect, not a
pipeline defect.

## Coverage and comparability

**Re-scored:** all 1,974 predictions, under one rule set, as required before any
comparison.

**Comparability caveat, stated plainly.** These predictions come from one stored
run at an unknown `code_revision` (the field is `null`). They are **not** a
current-engine measurement, and the atlas does not claim they are. Two separate
things are recorded per failure:

- `rescored_correct` / `predicted_answer` — the **stored reader prediction**,
  re-scored with the fixed scorer
- `engine_claims` / `engine_detail` — what the **current deterministic engines**
  do on the same frozen context

Those are different systems, and conflating them is exactly the mistake this
audit exists to prevent.

## Live-engine check on the failure set

Running the current committer over the 987 failures on the frozen context:

```
abstain  693
wrong    180
correct  114
```

So **114 of 987 stored failures (11.6%) are already answerable** by the engines as
they stand. This is a *capability ceiling* figure for the current engines, not a
score improvement: it says the engines can now solve 114 questions that this
stored run got wrong, and nothing about how the full pipeline would score.

## Unknowns — not filled with guesses

- The stored run's `code_revision` is `null`; its prompt condition and engine
  wiring are unknown.
- Whether the stored predictions' retrieval context matches the frozen cache
  used here is unverified. The cache is a separate artifact.
- For 9 F2 records `gold_in_context` is `unknown` because no cache row could be
  resolved for them.
- `E` class (gold genuinely absent from the conversation) is inferred from
  context presence only. Absence from the *compiled context* is weaker evidence
  than absence from the *conversation*; a full E classification needs the raw
  conversation, which this atlas did not check.
